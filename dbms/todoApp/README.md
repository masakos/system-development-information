# TODOアプリで学ぶデータベース設計

## 目標

TODOアプリを題材に、データベース設計の基本を学びます。

- アプリで扱うデータを整理できる
- データの関係を考え、ER図を作成できる
- 主キー（PK）と外部キー（FK）の役割を説明できる
- SQLを使ってデータの登録・検索・更新・削除ができる
- ビュー・インデックス・ストアドプロシージャ（トリガー）の役割を説明できる

---

## 1. TODOアプリを観察しよう

### 1-1. TODOアプリとは？

TODOアプリは、やるべきことを登録し、管理するためのアプリです。

例えば、次のような使い方をします。

- 学校の課題や提出物を管理する
- 仕事で必要な作業を管理する
- 買い物やプライベートの予定を管理する

今回作成するデータベースでは、複数のユーザーがそれぞれ自分のTODOを管理できるものとします。

また、TODOを「学校」「仕事」「プライベート」などのカテゴリに分類できるようにします。

### 1-2. アプリの機能を確認しよう

次の機能を持つTODOアプリを想定します。

| No. | 機能           | 内容                               |
| --- | -------------- | ---------------------------------- |
| 1   | ユーザー登録   | アプリを利用するユーザーを登録する |
| 2   | TODO登録       | やるべきことを登録する             |
| 3   | カテゴリ分類   | TODOをカテゴリに分類する           |
| 4   | TODO一覧       | 自分のTODOを一覧表示する           |
| 5   | 完了状態の変更 | 未完了のTODOを完了にする           |
| 6   | TODOの編集     | タイトルや期限を変更する           |
| 7   | TODOの削除     | 不要になったTODOを削除する         |

### 問1　どのようなデータが必要だろう？

上記の機能を実現するために、データベースに保存する必要がある情報を考えましょう。

**回答例**

| 値                | 何のデータか               |
| ----------------- | -------------------------- |
| DBの課題          | タイトル（TODO）           |
| 演習問題を解く    | 詳細                       |
| 2026-10-30        | 期限                       |
| 学校              | カテゴリ                   |
| 田中              | ユーザー（登録した人）     |
| □（チェックなし） | 完了フラグ（未完了）       |

## 2. データを整理しよう

### 2-1. TODOの情報を考える

例えば、次のTODOを登録するとします。

| 項目             | 内容                           |
| ---------------- | ------------------------------ |
| タイトル         | データベースの課題を提出する   |
| 詳細             | 演習問題1～5を解く             |

このTODOを管理するには、タイトルや期限だけでなく、誰が登録したのか、どのカテゴリに属するのかという情報も必要です。

ユーザーごとにTODOを管理するには、ユーザーの情報も必要です。また、カテゴリを自由に追加・変更できるようにするには、カテゴリの情報も管理する必要があります。

## 3. テーブルを設計しよう

### 問2　テーブルに必要な項目を考えよう

TODOを管理するために、どのような項目が必要でしょうか。

次の手順で、テーブルを設計しましょう。

1. 必要なテーブルを考える
2. 各テーブルに必要なカラム（項目）を考える
3. 主キー（PK）と外部キー（FK）を設定する
4. テーブル間のリレーションシップを図で表す

#### （参考）SQLiteのデータ型

| ストレージクラス | 説明                       | 例                  |
| ---------------- | -------------------------- | ------------------- |
| `NULL`           | 値が存在しない             | `NULL`              |
| `INTEGER`        | 整数                       | `10`, `-5`, `0`     |
| `REAL`           | 浮動小数点数（小数）       | `3.14`, `98.5`      |
| `TEXT`           | 文字列                     | `'田中'`, `'Hello'` |
| `BLOB`           | バイナリデータ（バイト列） | 画像、音声など      |

### 3-1. テーブル設計（回答例）

**users**

| 項目名 | 意味           | 値の例 | PK/FK | データ型 |
| ------ | -------------- | ------ | ----- | -------- |
| id     | ユーザーの番号 | 1      | PK    | INTEGER  |
| name   | ユーザー名     | 田中   |       | TEXT     |

**categories**

| 項目名 | 意味           | 値の例 | PK/FK | データ型 |
| ------ | -------------- | ------ | ----- | -------- |
| id     | カテゴリの番号 | 1      | PK    | INTEGER  |
| name   | カテゴリ名     | 学校   |       | TEXT     |

**tasks**

| 項目名       | 意味                              | 値の例         | PK/FK | データ型 |
| ------------ | --------------------------------- | -------------- | ----- | -------- |
| id           | タスクの番号                      | 1              | PK    | INTEGER  |
| title        | タイトル                          | DBの課題       |       | TEXT     |
| description  | 詳細                              | 演習問題を解く |       | TEXT     |
| deadline     | 期限                              | 2026-10-30     |       | TEXT     |
| is_completed | 完了フラグ（0：未完了、1：完了）  | 0              |       | INTEGER  |
| user_id      | 登録したユーザーの番号            | 1              | FK    | INTEGER  |
| category_id  | カテゴリの番号                    | 1              | FK    | INTEGER  |

> **カラム名の付け方：`is_completed` と `status`**
>
> - 完了・未完了の2択だけ → `is_completed`
>   - 「完了しているか？」という Yes / No で判断できる状態を表す名前
>   - 値が true（1）なら完了、false（0）なら未完了と直感的に理解できる
> - 未着手・進行中・完了など複数の状態 → `status`

### 3-2. ER図（回答例）

```
┌──────────────┐ 1        0..* ┌──────────────────┐ 0..*        1 ┌──────────────┐
│ users        │───────────────│ tasks            │───────────────│ categories   │
├──────────────┤               ├──────────────────┤               ├──────────────┤
│ PK id        │               │ PK id            │               │ PK id        │
│    name      │               │    title         │               │    name      │
└──────────────┘               │    description   │               └──────────────┘
                               │    deadline      │
                               │    is_completed  │
                               │ FK user_id       │
                               │ FK category_id   │
                               └──────────────────┘
```

- **ユーザーとタスク**：1対多（1人のユーザーが0件以上のタスクを持つ。タスクは必ず1人のユーザーに属する）
- **カテゴリとタスク**：1対多（1つのカテゴリに0件以上のタスクが属する。タスクは必ず1つのカテゴリに属する）
- **外部キーの配置**：「多」側の `tasks` に `user_id` と `category_id` を置く
  （「1」側の `users` にタスクのidを置くと、1人が1件のタスクしか持てなくなるため）
- **主キーの役割**：テーブルの中の各行を一意に区別するため。同名のユーザーがいても区別でき、外部キーから参照する対象にもなる

## 4. データベースを作成しよう（CREATE TABLE）

ここからは、SQLiteを使ってデータベースを作成します。

今回の設計では、次の3つのテーブルを作成します。

| テーブル名 | 管理するデータ |
| ---------- | -------------- |
| users      | ユーザー       |
| categories | カテゴリ       |
| tasks      | TODO           |

### CREATE TABLE文の基本構文

テーブルを作成するSQL文です。カラム名・データ型・制約を半角スペースで区切って記述します。

```sql
CREATE TABLE テーブル名 (
    カラム名 データ型 制約,
    カラム名 データ型 制約,
    ...
);
```

- `CREATE TABLE`：テーブルを作成する命令
- テーブル名：作成するテーブルの名前
- カラム名：項目の名前
- データ型：格納するデータの種類
- 制約：データを登録するときのルール

#### 制約（データのルール）

| 制約          | 意味         | 説明                                 |
| ------------- | ------------ | ------------------------------------ |
| `PRIMARY KEY` | 主キー       | レコードを一意に識別する             |
| `NOT NULL`    | NULL禁止     | 必ず値を入力する                     |
| `UNIQUE`      | 一意制約     | 同じ値を重複して登録できない         |
| `DEFAULT`     | 初期値       | 値を指定しない場合の初期値           |
| `FOREIGN KEY` | 外部キー     | 他のテーブルの主キーを参照する       |
| `CHECK`       | 値のチェック | 指定した条件を満たす値だけ登録できる |

### 4-1. テーブルを作成する

次のSQLを実行してください。

```sql
-- SQLiteでは、外部キー制約を有効にするために接続ごとに実行する
PRAGMA foreign_keys = ON;

CREATE TABLE users (
    id INTEGER PRIMARY KEY,
    name TEXT NOT NULL
);

CREATE TABLE categories (
    id INTEGER PRIMARY KEY,
    name TEXT NOT NULL UNIQUE
);

CREATE TABLE tasks (
    id INTEGER PRIMARY KEY,
    title TEXT NOT NULL,
    description TEXT,
    deadline TEXT,
    is_completed INTEGER NOT NULL DEFAULT 0,
    user_id INTEGER NOT NULL,
    category_id INTEGER NOT NULL,
    FOREIGN KEY (user_id) REFERENCES users(id),
    FOREIGN KEY (category_id) REFERENCES categories(id),
    CHECK (is_completed IN (0, 1))
);
```

## 5. データを登録しよう（INSERT）

### INSERT文の基本構文

テーブルに新しいデータ（レコード）を登録するSQL文です。

```sql
INSERT INTO テーブル名 (カラム名1, カラム名2, ...)
VALUES (値1, 値2, ...);
```

- `INSERT INTO`：データを登録する命令
- カラム名：値を登録するカラム（項目）
- `VALUES`：登録する値。カラム名と同じ順番で記述する
- 複数行をまとめて登録する場合は、`( ... ), ( ... )` のようにカンマで区切る

### 5-1. ユーザーを登録する

```sql
INSERT INTO users (id, name)
VALUES
    (1, '田中'),
    (2, '鈴木');
```

2人のユーザーが登録されます。

### 5-2. カテゴリを登録する

```sql
INSERT INTO categories (id, name)
VALUES
    (1, '学校'),
    (2, '仕事'),
    (3, 'プライベート');
```

### 5-3. TODOを登録する

## 6. データを検索しよう（SELECT）

### SELECT文の基本構文

テーブルからデータを取り出すSQL文です。

```sql
SELECT カラム名1, カラム名2, ...
FROM テーブル名
WHERE 条件;
```

- `SELECT`：取り出すカラムを指定する。`*` を指定するとすべてのカラムを取り出す
- `FROM`：データを取り出すテーブルを指定する
- `WHERE`：取り出す行の条件を指定する（省略するとすべての行が対象）

### 6-1. TODOの一覧を表示する

```sql
SELECT id, title, deadline, is_completed
FROM tasks;
```

このSQLでは、TODOのID、タイトル、期限、完了状態を表示します。

### 6-2. ユーザー名とカテゴリ名も表示する

`tasks` テーブルにはユーザー名やカテゴリ名ではなく、ユーザーIDとカテゴリIDが保存されています。

ユーザー名やカテゴリ名を表示するには、`JOIN` を使ってテーブルを結合します。

```sql
SELECT
    tasks.title,
    users.name AS user_name,
    categories.name AS category_name,
    tasks.deadline,
    tasks.is_completed
FROM tasks
JOIN users
    ON tasks.user_id = users.id
JOIN categories
    ON tasks.category_id = categories.id;
```

- `JOIN テーブル名 ON 結合条件`：結合条件に一致する行どうしをつなげる
- `AS 別名`：表示するカラムに別名を付ける

## 7. データを更新しよう（UPDATE）

TODOの完了状態や期限は、後から変更できます。

### UPDATE文の基本構文

テーブルに登録されているデータを変更するSQL文です。

```sql
UPDATE テーブル名
SET カラム名1 = 値1, カラム名2 = 値2, ...
WHERE 条件;
```

- `UPDATE`：データを更新する命令
- `SET`：変更するカラムと新しい値を指定する。複数のカラムはカンマで区切る
- `WHERE`：更新する行の条件を指定する

> **注意**
>
> `UPDATE` 文で `WHERE` を省略すると、条件で行を絞り込めず、**すべての行が更新されます**。
> 実行前に `SELECT` 文で更新対象を確認しましょう。

### 7-1. TODOを完了にする

田中が登録した「DBの課題」を完了にしてみましょう。

```sql
UPDATE tasks
SET is_completed = 1
WHERE id = 1;
```

実行後、次のSQLで確認します。

```sql
SELECT * FROM tasks
WHERE id = 1;
```

`is_completed` が `1` になっていれば成功です。

### 7-2. 期限を変更する

「Javaの復習」の期限を変更します。

```sql
UPDATE tasks
SET deadline = '2026-11-02'
WHERE id = 2;
```

### 問4　タイトルを変更しよう

「買い物」のタイトルを「食料品の買い物」に変更してください。

変更後、データが正しく更新されているか確認してください。

## 9. 外部キーの役割を確認しよう

外部キーは、テーブル間のデータの整合性を保つために使います。

例えば、存在しないユーザーIDを指定してTODOを登録しようとすると、外部キー制約によって登録が拒否されます。

```sql
INSERT INTO tasks
    (id, title, user_id, category_id)
VALUES
    (99, 'テスト用TODO', 999, 1);
```

このSQLは、ユーザーID `999` が `users` テーブルに存在しないため、エラーになります。

> **補足**
>
> SQLiteでは、`PRAGMA foreign_keys = ON;` を実行していないとエラーになりません。
> エラーにならない場合は、`PRAGMA foreign_keys = ON;` を実行してから再度試してみましょう。

## 11. ビュー（VIEW）

### 11-1. ビューとは？

6-2では、ユーザー名やカテゴリ名を表示するために、`JOIN` を使った長いSQLを書きました。
TODO一覧を表示するたびに、このSQLを毎回書くのは大変です。

**ビュー**は、`SELECT` 文に名前を付けて保存したものです。
ビューを作成すると、テーブルと同じように `SELECT * FROM ビュー名` で結果を取り出せます。

- ビュー自体はデータを持たない（**仮想的なテーブル**）
- ビューを使うたびに、保存された `SELECT` 文が実行される
- 元のテーブルのデータが変わると、ビューの結果も自動的に変わる

| メリット             | 説明                                                             |
| -------------------- | ---------------------------------------------------------------- |
| SQLを簡単にできる    | 複雑な `JOIN` などを毎回書かなくてよい                           |
| 見せるデータを制限   | 必要なカラムや行だけを見せることができる（セキュリティ）         |
| 変更に強い           | テーブルの構造が変わっても、ビューを直せば利用側はそのまま使える |

### CREATE VIEW文の基本構文

```sql
CREATE VIEW ビュー名 AS
SELECT 文;
```

- `CREATE VIEW`：ビューを作成する命令
- `AS` の後に、保存する `SELECT` 文を書く

ビューを削除するときは、次のように書きます。

```sql
DROP VIEW ビュー名;
```

### 11-2. TODO一覧のビューを作成する

6-2のSQLを、`task_list` という名前のビューにします。

```sql
CREATE VIEW task_list AS
SELECT
    tasks.id,
    tasks.title,
    users.name AS user_name,
    categories.name AS category_name,
    tasks.deadline,
    tasks.is_completed
FROM tasks
JOIN users
    ON tasks.user_id = users.id
JOIN categories
    ON tasks.category_id = categories.id;
```

作成したビューは、テーブルと同じように使えます。

```sql
SELECT * FROM task_list;
```

さらに、`WHERE` で絞り込むこともできます。田中さんのTODOだけを表示してみましょう。

```sql
SELECT * FROM task_list
WHERE user_name = '田中';
```

**実行結果**

| id | title        | user_name | category_name | deadline   | is_completed |
| -- | ------------ | --------- | ------------- | ---------- | ------------ |
| 1  | DBの課題     | 田中      | 学校          | 2026-10-30 | 1            |
| 5  | レポート作成 | 田中      | 学校          | 2026-11-10 | 0            |
| 7  | 映画を見る   | 田中      | プライベート  | 2026-11-15 | 0            |

`JOIN` を書かなくても、ユーザー名とカテゴリ名つきの一覧を表示できました。

### 11-3. 未完了のTODOだけを表示するビュー

TODOアプリでは「まだ終わっていないTODO」をよく表示します。
未完了のTODOだけを取り出すビューを作成しましょう。ビューの中で、別のビュー（`task_list`）を使うこともできます。

```sql
CREATE VIEW incomplete_tasks AS
SELECT id, title, user_name, category_name, deadline
FROM task_list
WHERE is_completed = 0;
```

期限が近い順に表示します。

```sql
SELECT * FROM incomplete_tasks
ORDER BY deadline;
```

> `ORDER BY カラム名` で、指定したカラムの順に並べ替えます（`DESC` を付けると逆順）。

**実行結果**

| id | title        | user_name | category_name | deadline   |
| -- | ------------ | --------- | ------------- | ---------- |
| 8  | 歯医者の予約 | 鈴木      | プライベート  | 2026-11-08 |
| 5  | レポート作成 | 田中      | 学校          | 2026-11-10 |

## 12. インデックス（INDEX）

### 12-1. インデックスとは？

本の巻末にある「索引（さくいん）」を思い浮かべてください。
索引がない本で「外部キー」という言葉を探すには、最初のページから順番に読むしかありません。
索引があれば、「外部キー → 52ページ」とすぐにわかります。

データベースの**インデックス**も同じです。

- インデックスがない場合：テーブルの**すべての行を先頭から順番に調べる**（全件検索）
- インデックスがある場合：インデックスを使って、**目的の行をすぐに見つける**

| メリット                                   | デメリット                                                                       |
| ------------------------------------------ | -------------------------------------------------------------------------------- |
| `WHERE`・`JOIN`・`ORDER BY` の処理が速くなる | インデックスを保存するための容量が必要になる                                     |
|                                            | `INSERT`・`UPDATE`・`DELETE` のたびにインデックスも更新するため、少し遅くなる |

そのため、インデックスは「**検索条件によく使うカラム**」に作成します。

> **補足：自動的に作られるインデックス**
>
> `UNIQUE` 制約を付けたカラムには、自動的にインデックスが作られます。
> 今回の設計では `categories.name` に `UNIQUE` を付けているので、インデックスが自動で作られています。
> また、`INTEGER PRIMARY KEY` の主キーは、もともと高速に検索できる仕組みになっています。

### CREATE INDEX文の基本構文

```sql
CREATE INDEX インデックス名 ON テーブル名 (カラム名);
```

- `CREATE INDEX`：インデックスを作成する命令
- インデックス名：`idx_テーブル名_カラム名` のように、何のインデックスかわかる名前にすることが多い
- `ON テーブル名 (カラム名)`：インデックスを作成するテーブルとカラム

インデックスを削除するときは、次のように書きます。

```sql
DROP INDEX インデックス名;
```

### 12-2. どのカラムにインデックスを作るか考える

TODOアプリでは、「自分のTODO一覧」を表示する機能（機能4）を何度も使います。
このとき実行されるのは、次のようなSQLです。

```sql
SELECT * FROM tasks
WHERE user_id = 1;
```

`tasks.user_id` は検索条件によく使われ、`JOIN` の結合条件にも使われるので、インデックスを作る候補になります。

## 13. ストアドプロシージャとトリガー

### 13-1. ストアドプロシージャとは？

**ストアドプロシージャ**は、複数のSQLをひとまとめにして名前を付け、**データベースの中に保存した処理**です。
プログラムの「関数（メソッド）」のように、名前を指定して呼び出すと、保存した処理がまとめて実行されます。

| メリット           | 説明                                                                   |
| ------------------ | ---------------------------------------------------------------------- |
| 処理を再利用できる | 同じ処理を、複数のアプリから同じ名前で呼び出せる                       |
| 通信量が減る       | 複数のSQLを1回の呼び出しで実行できる                                   |
| ルールを統一できる | 「TODOを完了にするときは必ずこの処理を行う」などを、DB側で決められる |

> **注意：SQLiteはストアドプロシージャに対応していません**
>
> ストアドプロシージャは、MySQL、PostgreSQL、Oracle、SQL Server などのデータベースで使える機能です。
> SQLiteはアプリに組み込んで使う軽量なデータベースのため、ストアドプロシージャの機能はありません。
>
> ここでは、まず**MySQLでの書き方を参考として**紹介し、その後、SQLiteで使える似た機能である**トリガー**を実際に試します。

### 13-2. （参考）MySQLのストアドプロシージャ

MySQLでは、次のように書きます。**SQLiteでは実行できません。**

#### CREATE PROCEDURE文の基本構文（MySQL）

```sql
DELIMITER //

CREATE PROCEDURE プロシージャ名(IN 引数名 データ型, ...)
BEGIN
    SQL文;
    SQL文;
    ...
END //

DELIMITER ;
```

- `CREATE PROCEDURE`：ストアドプロシージャを作成する命令
- `IN 引数名 データ型`：呼び出すときに受け取る値（引数）
- `BEGIN` ～ `END`：まとめて実行するSQL文
- `DELIMITER`：処理の中で `;` を使うため、一時的にSQLの区切り文字を `//` に変更している

呼び出すときは `CALL` を使います。

```sql
CALL プロシージャ名(値, ...);
```
