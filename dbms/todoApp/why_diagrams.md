# なぜ図を描くのか？

TODOアプリでは、プログラムを作る前後に4つの図を描きました。

- [ER図](README.md)（README の 3-2）
- [クラス図](class_diagram.md)
- [シーケンス図](sequence_diagram.md)
- [アクティビティ図](activity_diagram.md)

「いきなりコードを書けばいいのでは？」と思った人もいるでしょう。
ここでは、**なぜ図が必要なのか** を考えます。

---

## 1. 家を建てるときを考えてみよう

家を建てるとき、大工さんはいきなり木を切り始めたりしません。
まず **設計図** を描きます。しかも、設計図は1枚ではありません。

| 家の設計図 | わかること |
| ---------- | ---------- |
| 間取り図 | どんな部屋が、いくつあるか |
| 配線図 | 電気がどこからどこへ流れるか |
| 生活動線図 | 住む人が、どんな順番で部屋を移動するか |

1枚の図にすべてを描き込むと、ごちゃごちゃして読めなくなります。
そこで、**知りたいことごとに図を分けて** 描きます。

システム開発でも同じです。

---

## 2. それぞれの図は「別の質問」に答えている

| 図 | 答えている質問 | TODOアプリでわかったこと |
| -- | -------------- | ------------------------ |
| ER図 | **どんなデータを保存するか？** | `users`・`categories`・`tasks` の3つのテーブルが必要。`tasks` に `user_id` を置く |
| クラス図 | **プログラムはどんな部品でできているか？** | `TodoApp`・`User`・`Category`・`Task` の4つのクラスが必要 |
| シーケンス図 | **部品どうしが、どの順番でやりとりするか？** | 一覧表示では `TodoApp` → `Task` → `Category` の順に呼び出す |
| アクティビティ図 | **処理はどんな手順・条件・くり返しで進むか？** | `completeTask` は全件を1件ずつ調べ、IDが一致したら完了にする |

ER図・クラス図は **「何があるか」（構造）**、
シーケンス図・アクティビティ図は **「どう動くか」（動き）** を表しています。

---

## 3. 図を描くと、何がうれしいのか？

### (1) コードを書く前に、間違いや抜けに気づける

TODOアプリの図を見直すと、次のようなことに気づけます。

**アクティビティ図から気づけること**

`completeTask` の図を見ると、「指定したIDのTODOが **見つからなかったら** どうなるのか？」が描かれていません。
実際のプログラムでも、存在しないIDを指定すると **何も起きず、エラーも出ません**。
ユーザーは「完了にしたつもり」になってしまうかもしれません。

**シーケンス図から気づけること**

`findTasksByUser` は、一覧を表示するたびに **すべてのTODOを1件ずつ** 調べています。
TODOが100万件に増えたら、とても遅くなりそうです。
これは README の「12. インデックス」で学んだ問題と同じです。

このような問題は、コードを書き終えてから見つけるより、**図の段階で見つけたほうが、ずっと簡単に直せます**。
図なら、消しゴムで消して描き直すだけで済むからです。

### (2) 他の人と同じイメージを共有できる

システムは、1人ではなくチームで作ることがほとんどです。

「TODOにはユーザーとカテゴリがあって、ユーザーは複数のTODOを持てて……」と言葉だけで説明しても、
人によって思い浮かべる形が違ってしまいます。

図にすれば、**全員が同じものを見ながら話せます**。
UML（クラス図・シーケンス図・アクティビティ図などの描き方の決まり）は世界共通なので、初めて会う人とも同じ図で話ができます。

### (3) 後から読む人の助けになる

半年後に自分のプログラムを読み返すと、「なぜこう作ったのか」を忘れていることがよくあります。
数千行のコードを読むより、図を1枚見るほうが、全体の形を早くつかめます。

## 4. 開発の流れの中での図の位置

今回の学習は、実際のシステム開発と同じ順番で進めています。

```
① アプリの機能を決める       （README 1-2：機能一覧）
        ↓
② 保存するデータを設計する   （ER図）
        ↓
③ プログラムの部品を設計する （クラス図）
        ↓
④ 動きを設計する             （シーケンス図・アクティビティ図）
        ↓
⑤ プログラムを作る           （Java・SQL）
```

上の段階ほど、間違いを直す手間が少なくて済みます。
⑤まで進んでから①の間違いに気づくと、②～⑤をすべて作り直すことになります。

---

## 5. 注意：図を描くこと自体が目的ではない

図は、**考えを整理し、人に伝えるための道具** です。

- すべての図を、いつも描く必要はありません。今わからないこと・伝えたいことに合った図を選びます
- 細かすぎる図は、読むのも直すのも大変です。今回 `TodoApp` のメソッドから引数を省いたように、**伝えたいことに必要な分だけ** 描きます
- プログラムを変えたら、図も直します。図とプログラムが違っていると、かえって混乱のもとになります
